# Jarvis PRD v1.9 — Context Capacity Handoff（上下文交接换会话）

**版本**：v1.9（drafting）
**前置版本**：v1.8（2026-05-04）
**核心新增**：自动检测当前对话上下文负担，超出收益时由 AI 交接内容到新会话继续。

---

## 0. 动机

PRD §9.5 定义了主 Agent 上下文预算分配（system / agent_profile / task_envelope / session_summary / recent_messages / memories / scratch），并通过 §9.5.2a 动态压缩策略在压力上升时压缩历史。

但**压缩有上限**：

```text
压缩 → Rolling Summary → token 减少
↓ 但每次压缩损失原始细节
↓ Session 长跑下来：
  Rolling Summary 越来越长 / 失真
  scratch 越来越挤
  每次 task 注入的固定槽位（agent_profile + tool_scope + memories 召回）几乎不变
  ↓
  净收益 = 模型输出质量 − 上下文成本
  ↓
  当净收益 < 0 时，继续压同一个 session 已经亏本
```

PRD §14.4 已识别"压缩触发"，但没解决"压缩到极限后还要继续怎么办"。

**v1.9 的目标**：检测到这个临界点，由 AI 自己生成结构化交接文档，引导用户开新 session 续跑。

---

## 1. 核心新增：CapacityAdvisor

### 1.1 设计原则

```text
1. 静默观察 ≠ 默默积压：检测到的压力在用户察觉前就提示
2. 不强制：建议而非强迫。用户可以选择"继续凑合"或"交接换会话"
3. 交接是 AI 的责任：用户不应该手动写"上下文摘要"
4. 交接产物结构化：HandoffSnapshot 是后续 session 的冷启动输入
5. 与 §12.6 Dream / §15.7 raw_event_log 解耦：HandoffSnapshot 不替代它们
```

### 1.2 数据结构

```ts
type ContextHealth = {
  session_id: string
  trace_id: string

  // 当前消耗
  injected_tokens: number       // 本轮 hydrate 后真正喂给模型的 token 数
  budget_tokens: number         // ContextBudget.total_limit
  pressure_ratio: number        // injected / budget

  // 净收益评估（核心新增）
  effective_tokens: number      // 模型实际引用 / 输出质量贡献的 token 数
  noise_tokens: number          // 注入但未被引用的 token 数
  benefit_score: number         // (effective - noise) / injected，可负

  // 历史趋势（最近 5 次任务的 benefit_score 滑窗）
  benefit_trend: number[]
  declining: boolean            // 连续 3 次下降则标记

  // 触发标记
  advisory_level: "ok" | "warn" | "handoff_recommended" | "handoff_required"
}

type HandoffSnapshot = {
  id: string
  source_session_id: string
  target_session_id?: string    // 接续的新 session（建立后回填）
  trace_id: string
  generated_at: string

  // AI 主动生成的交接文档（结构化）
  sections: {
    title: string                          // 一句话总结当前任务
    completed_so_far: string[]             // 已经做完的关键步骤
    open_threads: string[]                 // 还在追的问题
    must_know_constraints: string[]        // 不要破坏的约束（CONTEXT.md 同款）
    artifact_refs: string[]                // 应该带过去的 Artifact id
    memory_refs: string[]                  // 应该带过去的 Memory id
    suggested_first_message: string        // 建议用户在新 session 第一句话怎么说
  }

  // 透传到新 session 的 cold-start 槽位
  cold_start_payload: {
    rolling_summary_excerpt: string  // 只取与未完成任务相关的部分
    pinned_memory_ids: string[]      // tier 1 / 高频引用
    pinned_artifact_ids: string[]
  }

  user_decision?: "accepted" | "declined" | "deferred"
  user_decided_at?: string
}
```

### 1.3 触发条件（advisory_level 分档）

```ts
function evaluate(health: ContextHealth): AdvisoryLevel {
  // ok：压力低，没有持续下降
  if (health.pressure_ratio < 0.5 && !health.declining) return "ok"

  // warn：单次净收益偏低，但不一定要换会话
  if (health.benefit_score < 0.4 && health.pressure_ratio < 0.7) return "warn"

  // handoff_recommended：触发用户提示
  // 任一条件：
  //   1. benefit_score 连续 3 次下降且 < 0.3
  //   2. pressure_ratio > 0.85 且 Rolling Summary > 1500 tokens
  //   3. 模型已被升级到 opus 但 benefit_score 仍 < 0.4
  if (handoffRecommended(health)) return "handoff_recommended"

  // handoff_required：硬性建议，不交接会持续掉线
  //   pressure_ratio > 0.95 且 force_compress 已触发 ≥3 次
  if (handoffRequired(health)) return "handoff_required"

  return health.advisory_level
}
```

### 1.4 AI 主导交接流程

```text
CapacityAdvisor 检测到 advisory_level >= handoff_recommended
  ↓
不直接打断用户，而是在下次 Agent 输出末尾追加：
  "[ℹ️] 当前会话上下文已经接近承受上限（净收益连续 3 次下降至 0.28）。
       要不要让我把目前的进展和未完成的事整理成交接文档，
       开个新会话继续？整理大约需要 5 秒。"
  ↓
用户回复 "好" / "yes" / "交接" / 点 [接受] 按钮
  ↓
HandoffPlanner 启动（独立子 Agent，使用更强模型）：
  读取 Rolling Summary + 最近 30 条 raw events + Task Tree + Artifact Index
  生成 HandoffSnapshot.sections（标题 / 已完成 / 待办 / 约束 / 参考资料 / 建议第一句）
  写入 handoff_snapshots 表（不可变）
  ↓
推送给用户预览：
  ┌────────────────────────────────────────────┐
  │ 📋 [ai 来源会话标题] 交接文档                │
  ├────────────────────────────────────────────┤
  │ ✦ 还在追：sync_executor.dart 的接口兼容    │
  │ ✦ 已完成：sync_state.dart / 单测 12/12 过  │
  │ ✦ 不要破坏：stream 接口（行 78-92）         │
  │ ✦ 建议下句：「继续 sync_executor 重构...」 │
  │                  [开新会话继续] [取消]      │
  └────────────────────────────────────────────┘
  ↓
用户确认 → 自动建立新 session：
  - session_action = create_new
  - 新 session.cold_start_snapshot 注入 HandoffSnapshot.cold_start_payload
  - 新 session 的第一条 user_message 是 suggested_first_message
  - HandoffSnapshot.target_session_id 回填
  ↓
旧 session 状态 → archived
旧 session.unresolved 中的项 → 已转移到新 session 的 unresolved
原 raw_event_log 不动（永久保留，PRD §15.7.2 不可变）
```

### 1.5 HandoffPlanner 的 token 预算

PRD §9.5 的子 Agent 预算分配适用，但 HandoffPlanner 有专项规则：

```ts
const HANDOFF_PLANNER_BUDGET = {
  total_limit: 16000,              // 高于普通子 Agent，需要看完老会话
  reserved_for_output: 4000,       // 留给生成的 sections JSON
  injected_old_summary: 2000,      // 老 Rolling Summary
  injected_recent_raw: 4000,       // 最近 30 条 raw events
  injected_task_tree: 1500,        // Task Tree 当前视图
  injected_artifacts: 1500,        // Artifact Index（仅 title + summary）
  scratch: 3000,
}

// 模型选择：handoff 任务是一次性高质量生成，强制 sonnet+
// （不走 §9.5.2b 的动态降级）
```

### 1.6 反向规则：什么不该自动交接

```text
不要触发自动交接：
  ❌ 用户正在 waiting_user 等子 Agent 确认（先解决等待中的事）
  ❌ pressure 临时高但 benefit_score 仍 > 0.5（一次复杂任务，不是会话病了）
  ❌ 60 秒内已建议过一次（避免反复打扰）
  ❌ Steer 信号刚注入（让 Agent 先消化）

不要无确认就执行：
  ❌ 自动 archive 旧 session（必须用户点确认）
  ❌ 跨 user 边界（profiles/ 不同的两个用户）
```

### 1.8 数据库 schema 增量

```sql
CREATE TABLE handoff_snapshots (
    id                       TEXT PRIMARY KEY,
    source_session_id        TEXT NOT NULL,
    target_session_id        TEXT,                    -- 用户接受后回填
    trace_id                 TEXT,
    sections_json            TEXT NOT NULL,           -- HandoffSnapshot.sections
    cold_start_payload_json  TEXT NOT NULL,
    user_decision            TEXT NOT NULL DEFAULT 'pending',
                                                      -- pending / accepted / declined / deferred
    advisory_level           TEXT NOT NULL,
                                                      -- handoff_recommended / handoff_required
    benefit_score            REAL NOT NULL,
    pressure_ratio           REAL NOT NULL,
    generated_at             TEXT NOT NULL,
    decided_at               TEXT
);

CREATE INDEX idx_handoff_source     ON handoff_snapshots (source_session_id, generated_at DESC);
CREATE INDEX idx_handoff_pending    ON handoff_snapshots (user_decision, generated_at DESC);

-- 不可变（同 PRD §15.7 三表的 trigger 模式）
CREATE TRIGGER prevent_handoff_update
    BEFORE UPDATE ON handoff_snapshots
    WHEN OLD.user_decision NOT IN ('pending', 'deferred')
    BEGIN SELECT RAISE(ABORT, 'handoff_snapshots is immutable once decided'); END;
```

## 3. 设计 Tradeoff

### 3.1 为什么不自动交接（不要用户确认）？

- 旧 session 的 raw_event_log 永久保留，但 ownership 切换是用户视角的"换房间"
- 自动切让用户失去掌控感（PRD 原则 12「最小化人类认知负担」≠「替人类做决定」）
- HandoffSnapshot 经常会丢上下文细节，需要用户先扫一眼才放心切

### 3.2 为什么 benefit_score 而非纯 pressure_ratio？

- 单纯 pressure 不能区分"这一轮任务复杂"和"会话整体老旧"
- benefit_score 看模型实际引用 / 输出质量，更接近"会话是否还在产生价值"
- 但 effective_tokens / noise_tokens 怎么算是工程难点（见 3.3）

### 3.3 effective_tokens 怎么测？

候选方案：
1. **简单**：模型输出对哪些注入内容做了引用（关键词重叠 / 实体重合）
2. **中等**：在 prompt 里强制要求模型在结尾输出 `references: [memory_id, artifact_id, ...]`，统计长度
3. **复杂**：embedding 相似度，比较输入注入向量和输出向量的内积

v1.9 第一版用方案 2（简单 + 可观测）。模型已经在用各种 schema 输出，多加 references 字段不算重负担。
